## 1. 系统/方法概述

本仓库**没有使用任何第三方日志框架**（未引入 `logging`、`loguru`、`structlog`、`python-json-logger` 等），后端 FastAPI 应用也未配置 Uvicorn 日志。所有“日志”输出通过两种机制实现：

- **运行时事件（RunEvent）**：由 `server/app/runner.py` 中的 `emit(db, run_id, type_, node_id, node_run_id, payload)` 统一写入 `run_event` 表，事件类型包括 `workflow_started/workflow_completed/workflow_failed`、`node_started/node_completed/node_skipped/node_failed`、`agent_started/agent_completed/agent_failed`、`tool_call/tool_result`、`notification_sent`、`agent_mounts_resolved`、`agent_select` 等。这些事件是前端 SSE 回放和运行历史的核心数据源。
- **调用记录（CallRecord）**：由 `Ctx.call(kind, target, req, resp, latency, tokens)` 在 `runner.py` 中定义，用于记录节点内对 LLM、工具、知识库、MCP、工作流等的每次调用，包含请求摘要、响应摘要、状态、延迟毫秒、token 用量等结构化字段。

此外，Alembic 迁移脚本 `server/alembic/env.py` 通过标准库 `logging.config.fileConfig` 加载 Alembic 自身的日志配置，仅影响迁移过程，不影响业务服务。

前端（React/Vite）未集成浏览器端日志收集或上报逻辑，调试依赖浏览器控制台；E2E 脚本位于 `scripts/`，使用 Node.js 直接驱动 CDP，不经过应用日志通道。

## 2. 关键文件

- `server/app/main.py` — FastAPI 应用入口，注册路由、CORS、RBAC 中间件与健康检查，无日志初始化。
- `server/app/runner.py` — DAG 执行引擎 + 事件发射器 + worker/scheduler，集中定义 `emit`、`execute_run`、`create_run`、`start_worker`。
- `server/app/agent_runtime.py` — Agent 运行层，复用 runner 的 `emit`/`create_run`/`execute_run`，并定义 `_Ctx.call` 以记录 agent 侧调用。
- `server/app/models.py` — 定义 `RunEvent`、`CallRecord`、`NodeRun`、`Run` 等持久化模型，构成结构化日志的数据结构。
- `server/alembic/env.py` — 通过 `fileConfig` 加载 Alembic 日志配置。
- `docs/research/lightweight-workflow-system/09-runner-scheduler-worker-design.md`、`10-logs-events-observability.md` — 设计文档中对事件/可观测性的约定说明。

## 3. 架构与约定

- **事件即日志**：所有运行期可观测信息以 `RunEvent` 行记录，按 `run_id` + 单调 `sequence` 排序，前端通过 `/api/runs/{id}/events` 拉取并以 Last-Event-ID 重放。错误路径也通过 `emit(..., "workflow_failed", ...)` 产出结构化错误事件。
- **调用级细粒度追踪**：每个节点执行期间，`Ctx.current_node_run_id` 作为上下文，将 LLM/工具/知识库/MCP/子工作流调用落盘为 `CallRecord`，支持按节点维度回溯。
- **安全截断**：请求/响应摘要统一截断至 1000 字符（`str(req)[:1000]`），payload 中消息类字段限制 2000 字符，避免日志膨胀。
- **Mock 回退标记**：当未配置真实 LLM base URL 时，LLM 调用返回 `[mock:...]` 前缀内容，并在 `agent_mounts_resolved` 事件中携带 `routing="mock"`，便于区分生产与开发行为。
- **无进程级日志输出**：代码中不存在 `print()`、`logging.info()` 等标准输出日志；异常通过 `RunError` 抛出并由 `execute_run` 捕获后写回 Run.error 与 `workflow_failed` 事件。

## 4. 约定与约束

- **禁止散落 print/logging**：当前代码库中除测试辅助脚本外，无任何业务模块使用 `print` 或 Python 标准日志库；所有可观测性必须经由 `emit` / `Ctx.call` 写入数据库。
- **事件类型需语义化**：新节点家族新增可观测点时，应参照已有模式新增 `emit(db, run.id, "<event_type>", payload={...})`，保持事件名与 payload 结构的可查询性。
- **敏感信息截断**：调用记录与事件 payload 中均对字符串做长度限制，避免泄露长文本或密钥。
- **错误路径必须 emit**：`execute_run` 中 `except Exception` 分支强制设置 `run.status = "failed"` 并 `emit("workflow_failed")`，确保失败可被前端 SSE 感知。
- **Alembic 日志独立**：迁移阶段使用 `logging.config.fileConfig` 加载自身配置，不应与业务日志混用。

综上，该仓库的“日志系统”实质是一个**以数据库为中心的结构化事件与调用追踪体系**，而非传统意义上的进程日志框架。它通过 `RunEvent` 提供运行级审计，通过 `CallRecord` 提供节点级调用追踪，并通过前端 SSE 暴露给 UI 实时消费。
