## 0. 这套文档怎么用

1. **任何实现工作开始前**，必须按顺序：读本文件 → 读当前阶段规格 → 重读涉及源码（防止并行会话已改动）。
2. **规格即契约**：状态为"已冻结"的规格，实现不得偏离；确需偏离时，在该规格的"变更记录"一节追加说明（原因 + 影响），不许静默修改。
3. **验收即打勾**：每阶段完成后，对照其验收清单逐条核验，结果写入该规格"状态日志"，再更新本文件的状态看板。
4. **防忘三层**：本目录进 git；本文件的状态看板是唯一进度事实；助手持久记忆中有一条指向本文件的索引。

## 3. 阶段目标速览

### 3.0 最终交付目标（Definition of Done）
四阶段全部验收通过后，本仓库应满足调研 00 §15 的 MVP 验收口径，可机械验证为四个闭环：

1. **配置可保存可恢复**：三类 Agent 草稿带 revision，冲突 409 不静默覆盖，刷新可恢复。
2. **依赖可验证可冻结**：发布校验拦截失效依赖；版本快照冻结工具/模型/知识/成员版本，运行不漂移 latest。
3. **运行可观察可重放**：任一 Run 可定位 Agent 版本 + 资源版本；事件流可按 sequence 重放；autonomous 有流式与步骤；Flow/Group 有节点级状态回写。
4. **版本可发布可回滚**：发布产生不可变版本 + artifactHash；沙箱/线上独立部署记录；回滚不改历史。

外加两条卫生标准：**零假路径**（无假数据运行、无死配置、无门面控件）与**零双轨**（mock 残留清零，见 D-6）。
已登记偏差（单租户、Group 无置信度门控、可访问性后置、前端暂无单测）不计入缺口，见 §5.5。

### 3.1 阶段速览

- **A（约 1 周）**：修掉审计发现的 12 处错误实现，处置 8 处门面功能，清退 agent 搭建轨道的遗留 mock 路径。不引入新模型、不动架构。验收主题：**"页面上能做的，运行时都真实生效"**。
- **B（约 2 周）**：Agent 成为真正的聚合根——AgentVersion/Release/revision，运行认版本（发布产物真正被执行），CommonAgentConfig 一期（对话体验 + 结构化记忆声明），autonomous 异步化 + 流式预览 + 步骤面板。验收主题：**调研 §20 四个闭环全部闭合**。
- **C（约 2.5 周）**：Trace/Span + CONTROL/CONTENT 双通道；节点注册表 `editorKinds` 与 schema 驱动 Inspector；补齐节点（对话回复/记忆变量/Query改写/决策分类/工作流选择/代码沙箱等）；变量统一为结构化绑定。验收主题：**对标调研 §15.2–15.4 的运行验收**。
- **D（持续）**：Workspace Shell 四 Tab 三型统一、模型对比、观测指标/回放、评测 Judge、进化 Patch、RBAC/审计/租约锁、工程交付物（openapi/schema/错误码）、质检页面 mock 清退。验收主题：**企业治理面**。

## 4. 工作流规则

### 4.1 开工规则
1. 读本文件与阶段规格；确认看板状态与记忆索引一致。
2. 重读规格中列出的每个待改文件的**当前内容**（并行会话可能已改动；历史教训：不重读直接 Write 会覆盖他人工作）。
3. 规格中的文件路径若已失效，先定位再在"变更记录"中登记新位置。

### 4.2 完工规则（含证明机制）
1. 新增/修改测试全部通过（`pytest server/tests`），现有测试不回归。
2. 逐条过验收清单，产出**验收报告**；报告的每一项必须附证据，证据只认三类：
   - **自动证据**：仓库内稳定测试的名称（可被任何人重跑）；
   - **脚本证据**：可复制粘贴执行的命令 + 实际输出（含 `grep` 不存在性证明）；
   - **手工证据**：逐步复现步骤 + 观察结果（用于无自动化覆盖的 UI 项）。
   不接受"已确认/应该可以"这类自指性陈述。
3. 机器门禁（任何人可独立复核）：
   - `cd server && python -m pytest tests -q` 全绿；
   - `npm run build` 通过；
   - `node scripts/verify-fullstack.mjs` PASS（Phase A 起该脚本补充版本语义场景）；
   - 规格中列明的 `grep` 不存在性检查输出为空。
4. 用户逐项验收；验收结论写入规格"状态日志"与本文件看板。未通过项保持未勾选并写明原因——**宁可清单有未勾项，不做无证据的完成声明**。
5. 提交 git（验收项与 commit 可互查）；更新助手记忆索引中的阶段状态。

### 4.3 变更规则
- 冻结规格的偏离必须写入该规格"变更记录"节。
- 范围蔓延（规格外的新功能）默认拒绝；确有价值则登记到对应后续阶段的"候选项"。

### 5.1 错误契约（新代码一律遵守）
```json
{"code": "VALIDATION_FAILED", "message": "人类可读信息", "path": "nodes[2].config.prompt", "traceId": "..."}
```
HTTP 状态与业务状态一致（400/409/422 不再返回 200）；保留现有 409 revision 冲突语义。

### 5.2 事件命名
现有 `run_event.type` 词表保持；新增事件在所属阶段规格中登记。B 阶段起事件 payload 必须带 `runId`；C 阶段起增加 `channel/traceId/spanId`。

- 不实现调研中的客服工具节点（行业域）。
- 不做 QuickService 接口兼容层（调研 00 §1 明示不必复刻其接口命名）。

### 5.4 决策登记（规格间共享的架构决定）
- **D-1 草稿双库的冲突检测**：dialogue/group 型 Agent 的公共配置在 `agent.config`、图在绑定工作流的 `draft_definition`，两者各有 revision。B 阶段发布请求必须同时携带 `configRevision + graphRevision`，服务端任一不符即 409；版本快照落库在同一事务内读取两者。彻底方案（图并入 Agent 草稿、单一 revision）登记为 C/D 候选项，不在 B 范围内。此决策直接来自调研 00 §10.2 对 QuickService 双写漂移的结论。
- **D-2 单一 LLM 适配器**：B 阶段把 `runner._call_model` 与 `agent_runtime._chat_completion` 合并为单一模型调用模块（鉴权解析、mock 回落、流式/非流式唯一入口），此后禁止新增并行 LLM 调用路径。
- **D-3 单一前端 API 层**：所有页面经 `wf-api.ts`/`resource-api.ts` 访问后端；A-16 收编现存裸 fetch，此后禁止页面内新增裸 fetch。
- **D-4 运行树**：B 阶段为 `Run` 增加 `parent_run_id`；嵌套调用（成员 Agent、子工作流）必须挂载到父运行。顶层列表默认只显示 `parent_run_id IS NULL`。
- **D-5 容量与运行时底座决策点**：当前为单进程单 worker 原型。当**日 run 持续 ≥10 万或峰值 ≥50/s** 时触发容量加固：① worker 池（SKIP LOCKED 已支持多 worker，部署形态变化）② LLM I/O 并发化（线程池/asyncio）③ SSE 由盲轮询改 NOTIFY/Redis 唤醒 ④ run_event 按月分区 + 留存 TTL ⑤ emit 批量/预分配 sequence。若进一步要求**运行中崩溃精确续跑或多机分布式调度**，届时评估引入 Temporal 类持久化底座作为 worker 基座（运行语义与事件协议保持不变）。该评估不提前进行。
