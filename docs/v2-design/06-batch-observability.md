## 2. 成熟产品对标（一眼查看的共性做法）

| 产品 | 我们学什么 |
|---|---|
| **OpenAI Batch API** | 批次对象的极简核心：`request_counts{total, completed, failed}` 三数 + 状态生命周期（validating→in_progress→completed/failed/expired）+ 输出/错误文件分离。**"三个数 + 一个状态条"就是批次的最低完备摘要** |
| **Airflow Grid View** | 任务×批次的时间矩阵：一眼看"最近 N 次批次各自什么状态"，格子色块即状态，点格子下钻——任务视角看批次健康度的标准答案 |
| **Temporal Workflows** | 列表即运维面板：状态/开始时间/耗时/执行者一行说清，运行中条目带实时事件计数 |
| **LangSmith Runs / Arize** | 失败不是日志是**聚合**：按错误类型分组计数+代表样本；成本/时延/反馈在批次维度汇总 |
| **Dagster Backfills** | 大批次的进度语义：已完成/总数进度条 + 每秒速率 + 预计剩余 |
| **ReUI（我们自己的早期调研原型）** | 既定思想："一次触发=一个批次=一卡"，批次给出成功率、**失败集中度（error code 聚合）**、补数/立即运行按钮（`docs/sdd/prototypes/run-ops-prototype.html` 脚注）——本设计把它落实 |

## 3. 设计：四层一眼钻取（L0→L3）

不新增页面，把"一眼查看"做成四个层级的信息密度：

### L0 今日看板（已有，增强卡片信息密度）

卡片现结构保留（触发/环境标签、执行/投递双进度、异常摘要），增强：
- **分段进度条**：成功(绿)/失败(红)/处理中(蓝)/待处理(灰) 四段占比条，替代单一百分比——对齐 OpenAI `request_counts` 三数的可视化；
- **卡片角标增加**：`已处理 x/y`（依赖 §4 P1 的可信进度）与预计剩余时间（按当前速率外推，运行中才显示）；
- 需关注列卡片直接给出 **Top-1 错误类别 + 计数**（"超时 ×14"），不用点进去才知道出了什么事。

**视觉参考（用户指定）**：今日看板优先参考 shadcn kanban 页（`shadcnuikit.com/dashboard/apps/kanban`），其余页面（批次历史/批次详情等）从完整参考库 `shadcnuikit.com/dashboard/default` 中**逐页向用户确认**（格式见 00 §4-4）。此类 kanban 模板的通用形态是：横向状态列 + 卡片承载标题/标签徽标/进度/元信息 + 顶部工具条（搜索、视图切换）。[依据声明：该站点本次未能从审查环境访问，此处按 shadcn 系模板的通用形态描述，**HTML 原型阶段须人工对照原站校正**]。注意既有红线不变：不提供拖拽改状态（状态是系统事实）、不用成员头像、颜色不作唯一状态信号。

### L1 批次历史（已有，补两列+趋势）

- 表格补列：**成功/失败/跳过 三数**（OpenAI 式 request_counts）+ 耗时 + Token 合计；
- 行内错误摘要显示**最高频错误类别**而非原始字符串；
- 顶部加一条**任务级健康条**（可选筛选后）：最近 7 天批次成功率走势迷你图——把"这批任务最近稳不稳"提到列表层。

### L2 批次详情头部重设计（核心交付：5 秒看懂一批）

现头部是双徽标+8 概览卡（信息全但无主次）。V2 头部改为**一条状态带 + 三组一眼信息**：

```
┌────────────────────────────────────────────────────────────────┐
│ 质检任务·每日批  #TR-0912   [执行: 运行中] [投递: 待启动]       │
│ schedule · prod · v1.4 · 2026-09-04 02:00 触发                 │
│                                                                │
│ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░░░  1,412/2,000  已处理                    │
│ 成功 1,389 · 失败 14 · 跳过 9        速率 6.2条/s · 约剩 1分34秒│
│                                                                │
│ ⚠ 失败集中: LLM超时 ×9 · 输出schema不符 ×5   [看失败分析]      │
│ 用时 3分21秒 · Token 412k · 预计成本 ¥8.2     [重试失败] [取消] │
└────────────────────────────────────────────────────────────────┘
```

- 第一眼看**状态与进度**，第二眼看**成败分布**，第三眼看**失败集中度与成本**——对应"一眼查看"的三层；
- **失败集中行**是 ReUI 调研"失败集中度"的落地：错误按类别聚合计数（六分类×错误码二级），点击进失败分析 Tab（既有），Tab 内保持六分类聚合不变（SDD-13 验收项），但每类附 **3 条代表样本**（interaction_ref + 摘要）直接跳 Run 详情；
- 新增 **[取消]** 按钮（补 G4）：取消语义=停止派发新交互，已派发的 Run 各自取消，批次终态 `cancelled`（把那个无写入路径的列接上）；
- 8 概览卡降为下方"配置与上下文"折叠区（信息不删，降视觉优先级）。

## 4. 支撑后端改造（观测的前提是数据可信）

| # | 改造 | 说明 |
|---|---|---|
| P1 | **增量进度**：批次执行循环内每处理 N 条（或每 5s）增量更新 `processed_count`（新列）与成败计数；`total` 在读数完成后即写（先 `expected_count` 后精确值），看板/详情读增量列 | 修 G1；顺带给 Dagster 式速率/ETA 提供数据 |
| P2 | **结构化错误聚合**：新表/列 `task_run_error_agg(task_run_id, category, code, count, sample_refs[])`，Run 失败时增量累计（替代"前 20 条字符串"）；六分类沿用既有失败分析口径 | 修 G2；支撑失败集中行 |
| P3 | **跳过留痕**：`skipped` 记轻量事件（ref+原因码：window/sampling/duplicate/eligibility），只存计数摘要+抽样明细（不全量落行，避免大批次膨胀） | 修 G3；批次详情"跳过"可展开解释 |
| P4 | **批次取消 + 硬超时**：`POST /task-runs/{id}/cancel`；worker 派发循环每批检查取消标志（与单 Run 取消同机制）；`taskRunDeadlineSec` 从 DRAFT 转强制（超时→取消+终态 `failed/timeout`） | 修 G4 |
| P5 | **批次摘要端点**：`GET /operations/task-runs/{id}/summary` 一次返回三数+聚合+进度+成本，替代前端多处拼装；看板 SSE 改增量事件（状态变化的卡片才推），消灭 2s 全量重建+每卡 COUNT | 修 G7 |
| P6 | **批次级告警**：alerts 指标新增 `batch` 粒度（失败率阈值/超时/投递死信数），复用既有告警出站 | 修 G5 |
| P7 | **任务级聚合**：任务详情"最近批次"升级为 Airflow 式格子条（最近 14 批色块+悬停三数）+ 7 日成功率 | 修 G6 |

成本口径：Token 已在 `Run.token_usage`（`models.py`），批次维度求和即可；成本=Token×模型单价（模型资源已有配置位，缺单价字段则补）。

## 5. 实施顺序（建议）

1. **P1+P2+P5**（进度可信+错误聚合+摘要端点）→ L0/L1/L2 前端改版——这是"一眼查看"的最小闭环；
2. **P4**（取消+超时）→ 详情头部加按钮——运维刚需；
3. **P3+P7**（跳过留痕+任务格子条）→ 完整性；
4. **P6**（批次告警）→ 与 Trigger 观测（03 文档 §6）同批接入告警体系。

每步验收沿用三类证据闸门；前端改版过视觉回归（基线更新走人工确认流程）。

## 6. 明确不做（边界）

- 不把 Interaction Run 画成看板卡（SDD-13 明文排除，继续遵守）；
- 不做跨批次自动补数策略（补跑仍走 backfill 人工/触发器显式发起）；
- 不做看板拖拽改状态（状态是系统事实，调研参考图 Square UI 的拖拽不采纳——既有决策）；
- 不在批次层展示个人数据明文（脱敏原则不变）。
